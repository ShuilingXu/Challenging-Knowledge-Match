# UI 设计与人类操作逻辑 逐项审查

**审查对象**：知识挑战赛运营台（`src/App.jsx` 7697 行 + `src/TurtleSoup.jsx` + 3 份样式表 + 服务端状态机）
**审查日期**：2026-10-18
**审查范围**：后台（11 个页面）、参与端（手机）、大屏端（受控屏 / 直接用浏览器打开）、横切的导航与反馈
**审查方式**：逐页读代码 + 服务端状态机对账 + 现有截图（`docs/manual-latest-images/`、`docs/soup-*/`、`output/ui-review/`）交叉验证
**不含**：功能是否缺失（只审"已有功能好不好用"）、后端性能、安全

## 0. 一句话结论

> **这个系统的"能力"已经齐全，但它的界面是按"资源"（题库、奖品、大屏、参与者）组织的，不是按"人正在做什么"组织的。** 现场主持人真正需要的是一条随时间推进的操作线（赛前 → 开题 → 公布 → 下一题 → 收尾），而界面给的是 11 个平级入口、三层同名的"开始/暂停/结束"、以及一个把 23 个按钮同时摊开的页面。

两条贯穿全局的病根：

1. **没有"当前时刻唯一的下一步"**。每个页面都并列展示 5~8 个可点按钮，靠用户自己判断现在该点哪个；判断错了系统也不拦（确认框覆盖率极低，且不一致）。
2. **状态与操作强耦合**。暂停 = 重置、改稿 = 冻结控场、切稿 = 清空进度。用户的一个"调节"动作，会静默地销毁别的状态。

## 2. 你点名的两个问题，拆开看

### 2.1 「切换海龟汤需要先暂停再切换汤稿」

**现在真实发生的操作链**（代码实证，不是猜）：

```
① 点「回到候场 / 重置」          TurtleSoup.jsx:258  →  服务端 stage=LOBBY，已公开线索清空
② 汤稿面板自动展开（因为 waiting） TurtleSoup.jsx:243  open={waiting || playlistEditing}
③ 在"当前汤稿"下拉里选另一份      TurtleSoup.jsx:244-247  onChange 立刻调接口、立刻生效
④ 点「展示汤面」重新开始           TurtleSoup.jsx:257
```

四个动作里藏着 **一条没有写出来的规则**：下拉框只在 `stage === 'LOBBY'` 时可点（前端 `disabled={... !waiting ...}`，服务端也会 `throw conflict("请先回到候场，再切换汤稿")`，`TurtleSoupService.java:303`）。所以用户的体感就是"我必须先暂停/重置，才能换汤"。

**这个设计为什么会让人难受**

| 症状 | 代码原因 | 人的代价 |
|---|---|---|
| 换稿前必须"重置"，而重置是破坏性的 | `RESET` 直接 `stage="LOBBY"; selected.clear()`（`TurtleSoupService.java:185`） | 上一个故事已公开的线索全没了；如果还想回看，回不去 |
| 没有"我先准备好下一份"的概念 | 汤稿选择作用在当前正在播的活动状态上 | 主持人没法在前一个故事进行时把下一份汤稿摆好 |
| 换稿后翻页速度变回 15 秒/页 | `switchTemplate` 新建 `State` 走 4 参构造 → `Playback.initial()`（`TurtleSoupService.java:33, 42-44, 309`） | 每换一个故事都要重新调速度，且没有提示"速度已复位" |
| 保存汤稿也会重置速度 | `save()` 同样走 4 参构造（`TurtleSoupService.java:94`） | 改一个错别字就丢了自己的节奏设置 |
| 选择器藏在折叠区里 | `waiting` 为假时 `<details>` 收起 | 播放中的主持人根本看不到"换汤稿"这件事在哪 |
| 换稿没有确认 | `onChange` 直接提交 | 误触下拉 = 换掉整场正在讲的故事 |

**建议（改成一个动作）**

1. **把"换汤稿"做成一个动作，而不是一个状态前置条件。** 在播放控制条上放一个「切换汤稿」按钮，点开是抽屉：列出本会场汤稿 + 每份的第一句汤面作预览 + 一个显式确认「切换将清空已公开线索，从候场开始」。一次点击完成 `RESET + switchTemplate`，用户不需要理解 LOBBY。
2. **保留"准备下一份"的能力**：抽屉里允许把某份标记为"待播"，切换时用它；这样主持人可以趁线索讨论时先把下一份摆好。
3. **速度设置跨故事保留**：`Playback.initial()` 改为继承上一份的 `paceSeconds`（服务端一行：`new State(content, "LOBBY", 0, rev, List.of(), new Playback(false,0,now,0, previous.playback().paceSeconds(), null))`）。
4. **禁止误触**：汤稿下拉改成按钮 + 弹层（`select` 的 `onChange` 即提交是这里最危险的一点）。

> 顺带：因为"暂停会场"会把海龟汤状态也重置成候场（`ActivityService.java:818-827`），用户很可能把"暂停"和"回候场"混为一谈——这是 F1 造成的认知污染，先修 F1 再修 F4。

### 2.2 「海龟汤页面按钮过多、操作界面挤在一起」

**客观数字**（`src/TurtleSoup.jsx` 静态统计 + 运行时展开）：

| 区块 | 按钮数 | 说明 |
|---|---|---|
| 大屏播放控制 | 6 | 暂停/继续、上一页、下一页、从头播放、减速、加速 |
| 展示控制 | 2 + 1 开关 | 展示汤面、回到候场/重置、答案·汤底拨杆 |
| 交互线索板 | 每条线索 1 个 | 3 条 = 3 |
| 临时添加线索 | 2 | 保存为待展示、添加并立即公开 |
| 编辑汤稿 | 每条线索 1 个 + 2 | 3 条 = 5（移除×3、添加线索、保存汤稿） |
| 汤稿选择 | 1 + 1 | 选择本会场汤稿、保存选择 |
| 活动生命周期 | 1~2 | 暂停、结束 |
| **合计（3 条线索时）** | **23** | 另有 1 个下拉、4 个 textarea、N 个复选框 |

**"挤"的具体成因**（不是主观感受）：

1. **三套并列的操作模型同时铺开**：①播放（翻页/速度）②演出（展示汤面/答案开关/线索公开）③编辑（改汤稿）。这三件事的使用频率差两个数量级，但它们在页面上是同一视觉权重。
2. **首屏被播放控制条占满**。播放控制条是 `position: sticky`（`turtle-soup.css:138`），手机上约 200 px 高，永久吃掉 1/3 屏幕；现有截图 `docs/soup-pagination-2026-10-06/host-playback.png`（1265×712）里，首屏只到"本会场使用的汤稿"折叠条，"展示控制"和线索板都在折叠线以下。
3. **同一屏出现 3 个"看起来都是主要动作"的按钮**：展示汤面（primary）、添加并立即公开（primary）、保存汤稿（primary）。主色被用掉了 3 次，等于没有主色。
4. **预览面板抢占横向空间**：右侧"大屏内容预览"固定 `height: clamp(560px, 70dvh, 760px)`（`turtle-soup.css:152`），比一次能读完的内容高，把左侧主列挤到 1.2fr。

**建议（目标布局：3 层，不是 23 个按钮）**

```
┌──────────────────────────────────────────────────────────────┐
│ 演出条（sticky，≤96px）                                       │
│  ●进行中  《最后一班电梯》  ·  线索 3/8  ·  第 2/4 页  · 15s/页 │
│         [ ⏸ 暂停 ]  [ ▶ 下一份汤稿 ]        [ ⚙ 播放设置 ]    │
├───────────────────────────────────┬──────────────────────────┤
│ ① 唯一下一步（随阶段变的 1 个大按钮）│  大屏实时预览            │
│    候场 → [ 展示汤面 ]             │  （高度跟随视口，不再固定  │
│    推理中 → [ 放出汤底 ]           │    560~760）             │
│    已揭晓 → [ 回到候场 ]（需确认）  │                          │
├───────────────────────────────────┤                          │
│ ② 线索板（唯一常驻大区块，可滚动）   │                          │
│    每张卡：文字 + 一个状态胶囊       │                          │
│    「已公开/未公开」，点卡片切换     │                          │
├───────────────────────────────────┴──────────────────────────┤
│ ③ 工具箱（折叠，默认全收起）                                   │
│    ＋ 临时线索 ｜ 📚 本会场汤稿 ｜ ✎ 编辑汤稿 ｜ ? 查看汤底      │
└──────────────────────────────────────────────────────────────┘
```

四条具体改法：

1. **控制条只留 2 个按钮**：暂停/继续 + 上下文主按钮；上一页/下一页/从头/减速/加速放进「播放设置」弹层（这些是"偶尔调"的，不是"每秒点"的）。
2. **线索卡去掉按钮**：整卡可点 = 切换公开状态，卡片右上角显示"已公开/未公开"。3 条线索从 3 个按钮变成 0 个按钮，且点错范围更大、更不容易点歪。
3. **编辑汤稿移出控场页**：改成侧栏里的独立入口「汤稿编辑」（或右侧抽屉），只在候场可保存。控场页不再因为 `dirty` 而整体瘫痪（同时修掉 F6）。
4. **播放控制条高度封顶**：sticky 条高度 ≤ 96 px（单行语义 + 一排按钮），速度用 `− 15 秒 +` 的步进器而不是两个按钮。

## 3. 设计层（视觉与设计系统）的系统性问题

### F11 三套按钮颜色没有语义

`theme-soyo.css:113-152` 定义了 `primary`（棕）、`secondary`（米白）、`accent`（雾蓝），但全站没有把颜色和"重要性/危险性"绑定：

| 按钮 | 实际样式 | 它真正的重要程度 |
|---|---|---|
| 开题并计时 | secondary（最弱） | 高（每次开题必点） |
| 跳题并开始 | accent（蓝） | 中 |
| 下一题并开始 | secondary | 高 |
| 公布答案 | accent | 高、且不可逆 |
| 发布积分榜 | primary（最强） | 中、可逆 |
| 确认获奖并上屏 | secondary（最弱） | **最高、且发奖不可逆** |

**建议**：改成按语义分 4 档并全站只用这 4 档——`primary`（当前唯一主动作，一屏最多 1 个）、`default`（次要）、`ghost`（导航/工具）、`danger`（不可逆：结束活动、重置、作废奖品、删除）。建议把"发奖上屏""结束活动""重置"统一成 `danger` 并用确认弹层包裹。

### F12 禁用态不解释原因

全局只有一条规则：`button:disabled { cursor: not-allowed; opacity: .62 }`（`styles.css:3`）。而每页的 `disabled` 表达式都很长，例如海龟汤的主按钮 `disabled={disabled || waiting} = busy || dirty || !content || activity.status !== 'LIVE' || waiting`（`TurtleSoup.jsx:219, 257`）——5 个原因，界面上一个字都不说。页面上确实补了一两句提示，但位置在面板底部、字号 13px（`turtle-soup.css:146`），且只有部分面板有。

**建议**：抽一个 `ActionButton({ disabledReason })`：禁用时把按钮包一层 `title` + `aria-describedby`，并在按钮正下方显示一句 12px 的原因（"有未保存的汤稿修改"/"活动未开始"/"请先展示汤面"）。这一个组件能一次性消掉全站 30+ 处"灰了但不知道为什么"。

### F8 反馈位置不在视线里

`StatusNotice` 是文档流元素（`styles.css:504`），不是浮层。海龟汤页把它放在汤稿折叠条后面（`TurtleSoup.jsx:252-253`），而线索板的按钮在页面下方 1500 px 处——今天点"公开这条线索"，成功提示会出现在屏幕上方的屏幕外。答题控场同理：`InlineError` 在页首，`control-actions` 在页中。

**建议**：统一成一个右上角固定 toast 栈（3 秒自动消失，错误常驻直到手动关闭），成功/失败/信息三色。保留页内 `InlineError` 只用于"整页加载失败"这一种情况。

### F19 两套主题并行，CSS 已经进入"覆盖战"

| 文件 | 体积 | 规则 | 重复选择器 |
|---|---|---|---|
| `styles.css`（旧科技风） | 95 KB | 297 | 43 |
| `theme-soyo.css`（新暖色） | 51 KB | 404 | 72 |
| `turtle-soup.css` | 16 KB | 151 | 24 |

`turtle-soup.css` 里 `.soup-preview` 被定义了 3 次，其中 `position` 先 `sticky`（:30）后 `static`（:61, :151）；`.soup-controls` 先 sticky（:97）后 static（:137）；`.soup-screen` 的 `height` 有 4 处不同取值。结果是：**改任何一处布局，都不知道最终生效的是哪条**。旧主题还有一批没人接手的选择器（`.award-table` 9~10px 字号、`.status-pill` 9px、`.pool-rule` 9px，`theme-soyo.css` 里完全没有对应覆盖），导致"奖品与核销"页的表格看起来像另一个产品。

**建议**：
1. 短期：把 3 份 CSS 按"基础层 / 组件层 / 页面层"重排，删掉被后文覆盖的死规则（可以用 `npx lightningcss` 或手工 grep 定位同名选择器）。
2. 中期：建立 8~10 个 token（`--text-sm/base/lg`、`--space-1..6`、`--radius`、`--danger`），页面里禁止再写 px 字号与裸色值。
3. 字号统一：**管理端最小 13px**。现在 9px/10px/11px 仍大量存在（`styles.css:19,22,45` 等），在 1366×768 的控场笔记本上基本不可读。

### 其它一致性缺口（快修）

- **F14 假控件**：顶栏通知铃铛 `<Bell/><i/>`（红点）没有 `onClick`（`App.jsx:661-664`）——直接删掉或接上真实事件。
- **F14 重复控件**：顶栏两个下拉框都写 `setActivityId`（`App.jsx:645-660`），一个是"选择会场"、一个是"选择母活动或会场"。合并成一个树形选择器（分组 + `└` 缩进已经有了）。
- **F16 图标复用**：`题库与组卷` 和 `海龟汤汤稿` 都是 `CircleHelp`；`实时控场` 和 `海龟汤控场` 都是 `Radio`；`奖品与核销` 和 `抽奖控场` 都是 `Gift`（`App.jsx:105-117`）。11 个导航项里 3 对撞图标。
- **F17 重复标题**：`workspace()` 在每个功能页上方又打印一行"当前会场：XXX"（`App.jsx:452`），与面包屑重复，还额外套了一层 `.page-content` 导致上下 padding 叠加。
- **F18 标签页无法区分**：全站没有一处 `document.title` 赋值。开三个会场时三个标签页标题一模一样。
- **无键盘**：全站 0 个 `onKeyDown`、0 个 `accessKey`。现场主持人最需要的"空格 = 下一页"、"P = 暂停"、"Esc = 收起"都没有。

## 4. 操作逻辑层（人的动作顺序）的系统性问题

### F13 三层同名的"开始/暂停/结束"

`ActivityLifecycle`（`App.jsx:7173-7186`）在母活动页、会场页、每个功能控场页都渲染一次，按钮文字完全一样（`activity-flow.js:6-15`）：

- 母活动：草稿 → [`启用母活动`]
- 会场：草稿 → [`启用报名`] [`开始活动`]；进行中 → [`暂停`] [`结束`]
- 功能（答题/抽奖/海龟汤）：草稿 → [`开始活动`]；进行中 → [`暂停`] [`结束`]

控场页上的那一组，作用对象是**功能**，不是会场。主持人看到"进行中 [暂停] [结束]"，会以为自己在停整场活动。

**建议**：①控场页不再重复渲染整个生命周期，只显示一个只读状态胶囊 + 「返回会场」；②如果保留「暂停」，文案改成"暂停本环节"；③母活动/会场/功能三层的状态在页面上用 `母活动 › 会场 › 功能` 三级 chip 同时呈现（现在只有功能一个 chip）。

### F1 「暂停」不是暂停，是重置（P0）

- 会场/母活动暂停时，会**级联**把子活动置为 PAUSED 并把它们的控制状态写回 `LOBBY`（`ActivityService.java:245-255`）。
- 子活动是海龟汤时，还会把汤稿状态重写成 `LOBBY`、清空 `revealedClueIndexes`，并向大屏推"候场"（`ActivityService.java:818-827`）。

也就是说：工作人员为了"修一下麦克风"点了暂停，回到台上时线索没了、当前题的计时没了、大屏回到候场。**动作叫暂停，效果是重置，且没有确认。**

**建议**：拆成两个概念——
- 「暂停」= 冻结：保留 stage、保留计时（`pausedAt`），大屏显示"暂停中"蒙层，恢复后原样继续；
- 「重置环节」= 破坏性：单独一个 danger 按钮 + 确认弹层写明会清空什么。
服务端在 `changeActivityStatus` 的 PAUSED 分支里不要改子活动 control 状态（这一行为可以保留给"结束"）。

### F2 结束活动一键执行（P0）

`ActivityLifecycle` 的 `change(status)` 没有任何确认（`App.jsx:7176-7181`）。点「结束」直接 `FINISHED`，服务端再 `closeSubActivities` 关掉所有子活动（`ActivityService.java:257`）。之后无法回到 DRAFT，也没有"撤销结束"。

**建议**：`结束` 改为 danger + 二次确认（把"将结束 N 个会场 / M 个环节，且不可恢复"写进弹层）；更稳的做法是允许 `FINISHED → LIVE`（服务端放开该迁移）用于误点恢复。

### F3 破坏性操作的确认策略不一致

| 动作 | 是否确认 | 位置 |
|---|---|---|
| 删除题目组 | ✅ 原生 `confirm` | `App.jsx:1935` |
| 删除大屏设备 | ✅ 原生 `confirm` | `App.jsx:4124` |
| 删除模板 | ✅ 原生 `confirm` | `App.jsx:4158` |
| 作废奖品 | ✅ 原生 `confirm` | `App.jsx:3219` |
| 发奖并上屏 | ✅ 原生 `confirm` | `App.jsx:1461` |
| 结束活动 | ❌ | `App.jsx:7173` |
| **海龟汤回到候场/重置** | ❌ | `TurtleSoup.jsx:258` |
| **海龟汤切换汤稿** | ❌ | `TurtleSoup.jsx:244` |
| 公布答案（不可逆，玩家已看到） | ❌ | `App.jsx:1666` |

**建议**：定一条规则——**"会让台上观众看到的、或让数据不可恢复的"一律确认**，并统一用同一个 `<ConfirmDialog>`（不要原生 `confirm`，它没有标题、没有危险色、移动端样式不可控）。目前 10 处原生 confirm + 17 处自定义 Dialog 混用，键盘行为和可访问性都不一致。

### F7 答题控场没有"唯一主动作"

`App.jsx:1631-1690` 六个平级按钮：

```
[开题并计时] [跳题并开始] [下一题并开始] [公布答案] [发布积分榜] [确认获奖并上屏]
 secondary      accent        secondary     accent      primary       secondary
```

问题：
1. 前三个都是"开始某题并倒计时 30 秒"，区别只在用哪道题，用户必须读懂下拉框当前选中的是谁。
2. `公布答案`、`发布积分榜`、`确认获奖` 在任何 stage 下都可用（只判 `busy`），可以"没开题就公布答案"。
3. 倒计时写死 30 秒（`:1638, :1647, :1660, :1718`），不读题目自己的时长设置；现场"这一题要 60 秒"只能靠主持人喊。
4. 唯一的确认框在"发奖"上（`:1461`），恰恰是**最该有仪式感**的一步，却用了最朴素的 `window.confirm` + 纯文本名单。

**建议**：
- 按 stage 只显示"下一步"：`LOBBY/未开题 → [开题 (30s ▾)]`；`QUESTION_OPEN → [提前收卷] [公布答案]`；`ANSWER_REVEALED → [发布积分榜] / [下一题]`；`SCOREBOARD → [确认获奖并上屏]`。
- 其余动作收进「改题」「重开计时」的工具菜单。
- 倒计时改成 15/30/60/90 秒选择器，默认取题目的 `timeLimit`（如果没有就记住上次选择）。
- 发奖确认改成带名单的自定义弹层（现在把名单拼进 `confirm` 字符串，`:1455-1461`）。

### F6 改稿冻结控场（P0）

海龟汤的 `disabled` 包含 `dirty`（`TurtleSoup.jsx:219`），注释里也写了"有未保存的修改，请先保存汤稿"（`:268`）。但编辑器在一个默认收起的 `<details>` 里，用户很容易在候场时改两个字、然后发现所有按钮都灰了。更糟的是**没有任何离开保护**：全站 0 处 `beforeunload` / 路由拦截，切侧栏或关标签页，未保存的修改直接消失（汤稿编辑器与题库编辑器都一样）。

**建议**：①`dirty` 不要参与控场按钮的 `disabled`（编辑与演出解耦）；②保存动作改为自动保存（500 ms 防抖）+ 顶部"已保存"时间戳；③编辑器单独成页后，离开时用 `beforeunload` + 路由拦截提示。

## 5. 逐页梳理

> 每页三行：**这页要人做的事** → **现在的障碍** → **建议**。编号延续上文 F 系列。

### 5.1 登录 `/login`

- **要人做的事**：输入账号密码进入工作台。
- **障碍**：左半屏是纯装饰（"星辉主题 · 次元现场""让每一次相遇都成为新的乐章" + 3 个 tag + 装饰图），在 1366×768 的控场笔记本上占掉 55% 宽度；没有任何"我该用哪个账号"的提示，也没有找回/重置入口。
- **建议**：把左侧压缩到 30%（或窄屏直接隐藏），右侧表单加一句"使用活动管理员分配的账号登录"。若使用频率高（现场每场都要登录），考虑记住上次账号。

### 5.2 导航与顶栏

- **要人做的事**：在 11 个入口里找到"我现在要控制的东西"。
- **障碍**：①导航按资源类型分类（题库/奖品/大屏/参与者），不按"赛前-赛中-赛后"；②会场开启 3 个功能时侧栏 9 项，其中 3 项叫"控场"（答题控场/海龟汤控场/抽奖控场）视觉完全等价；③3 对重复图标（F16）；④顶栏两个重复下拉 + 一个假铃铛（F14）；⑤切活动类型时侧栏项会整体变形状（母活动 5 项 / 会场 9 项），人会失去方位感。
- **建议**：
  1. 侧栏改两段：**「本场演出」**（总览、答题控场、海龟汤控场、抽奖控场、大屏）与 **「资料与设置」**（题库、汤稿库、参与者、奖品、权限），中间加分隔和小标题。
  2. 当前会场用顶栏单一选择器（树形分组），删掉第二个。
  3. 删掉假铃铛，或换成真实的"连接状态/未读告警"。
  4. 侧栏底部加一个 **「即将进行」** 小块：显示下一件事（如"3 分钟后开始答题第 4 题"），这是控场人员最需要的一句话。

### 5.3 活动总览 / 母活动 / 会场

- **要人做的事**：知道这个会场现在什么状态、该点哪个功能进去。
- **障碍**：`MainActivityPage` 把"进入会场 / 编辑总题库 / 报名入口 / 大屏 / 修改会场功能"做成 5 个同款按钮横排（`App.jsx:682`），主次不分；功能卡片用"已开启/未开启"文字胶囊，未开启时给一句"请在活动管理中编辑本会场勾选"——这是一段需要跳页的说明，而不是一个"现在就去开启"的按钮（`App.jsx:683`）。
- **建议**：功能卡片未开启时直接给「开启此功能」按钮（跳转到对应编辑弹窗）；主按钮只留「进入会场」或「进入答题」，其余降为文字链。

### 5.4 活动管理

- 列表行承载 7 个以上动作（编辑、功能、成员、状态、复制、删除……），窄屏全部折叠进溢出菜单（`.row-action { display: none }`，`styles.css:41`），手机上等于没有动作入口。
- **建议**：改为"行点击进详情页"，列表只留 1 个主操作 + 1 个溢出菜单，手机上保留溢出菜单。

### 5.5 答题控场

见 F7（按钮并列、无 stage 门禁、倒计时写死）+ F13（生命周期层级混淆）+ F8（反馈位置）。

补充两条：

- **没有"下一件事"提示**。左下角"现场流程"是一个 4 步有序列表（`App.jsx:1723-1742`），只是把 stage 高亮一下，并没有告诉主持人"现在该点哪个按钮"。
- **右侧 aside 抢戏**：`上一题/下一题` 预览卡把**正确答案**直接印在控场页（`:1704-1708`）——如果控场画面被投到观众可见的屏幕上（很常见：主持人笔记本 HDMI 直连投影），答案就泄了。
  **建议**：答案默认打码（`点击显示`），或在设置里加"控场页隐藏答案"开关。

### 5.6 题库与组卷

**客观规模**：一页约 49 个可点控件、2.5~3 屏高；单题对话框 13~15 个控件、内容高 1.5k~1.7k px 却被限制在 `max-height: 700px` 的滚动区里（`styles.css:28`），保存按钮在视口外约 900px。

**（1）新建题预填"选项 A/B/C/D + 答案 B"，且默认已启用** — `emptyQuestion()`（`App.jsx:1757-1769`）
占位文案被写成了真值，于是 `required` 永远通过（`:2404`、`:2414`），只填题干就保存 = 题库里多出一道答案 B、已启用、能自动判分的假题，并立刻出现在控场下拉里（`:1509-1514`）。
→ 新建时留空只用 `placeholder`；保存前阻断式校验（≥2 选项、答案 ⊆ 选项）；"允许发布"默认关闭（先草稿）。

**（2）保存失败的报错被弹窗遮罩挡住** — 页面级 `error` 只在页首渲染（`:2158`），题组对话框（`:2601-2679`）和文本评分对话框（`:2680-2734`）内部没有 `InlineError`；`.dialog-backdrop` 是 `position:fixed; z-index:50`（`styles.css:28`）。
点"保存题组"后界面毫无变化，操作员会重复点或以为已保存。→ 每个 Dialog 内部固定一条错误/成功条，字段原地标红。

**（3）删题会污染题组，且无法修复（F23）** — 顺序列表把找不到的题显示为"题目已删除"（`:2635`），但该行只有上移/下移、没有移除（`:2636-2653`），下方选题器的数据源是 `questions`（`:2660`），所以已删题永远无法取消勾选；保存时照发这些 id，服务端 404（`ActivityService.java:1171-1175`），错误又被（2）挡住。
→ 删题时级联清理 `question_set_items` 并提示"该题出现在 2 个题组"；顺序列表每行补"✕移除"；题组行显示"有效 9 题 / 1 题已删除"。

**（4）"下发"是隐形上下线开关（F25）** — "保存后立即下发到当前活动"复选框（`:2665-2672`）：取消勾选保存会把活动清成"无题组"（`ActivityService.java:511-515`）；勾上会把别的题组取消下发（`:1189-1195`）；列表里的「下发」按钮点击零确认（`:2242-2251`）。
LIVE 中点另一个题组「下发」，若正在开放的那题不在新题组里，所有参与者提交直接失败（`ActivityService.java:633-637`），主持人端只看到"已答 0/N"。
→ 保存与下发彻底分离；下发改成独立按钮 + 弹层写明"将切换为《XX》共 N 题；当前第 N 题不在新题组，切换后参与者无法提交"；LIVE 时要求输入题组名确认。

**（5）题库页不知道活动正在直播（F28）** — `QuestionsPage` 拿到了 `activity`（`:1750`）却从不渲染状态；编辑/删除/启用开关与题库列表同页（`:2581-2590`、`:2070-2087`），服务端 `updateQuestion` 也不看活动状态（`ActivityService.java:559-580`）。
LIVE 中顺手取消当前开题那道题的"允许发布"→ 全场提交失败。→ LIVE 时常驻红色横幅；对当前 `state.questionId` 的题锁住答案/启用字段；PUT 加 `updatedAt` 乐观锁。

**（6）导入是"选文件即提交"（F26）** — `importQuestions` 选完文件立刻解析并提交（`:1824-1839`），无预览、无确认、成功后不写任何提示、无批次号、无法回滚；重复导入同一文件 = 题目翻倍（题库无重复检测）。
→ 上传前弹预览「将新增 48 道（单选 30/多选 12/文本 6），总数 148→196」+ 确认；成功后给"已导入 48 道 · 撤销本次导入"（服务端按 `importBatchId` 支持整批回滚）。

**（7）逐行错误是 fail-fast** — `parseQuestionImport` 在第一条不合法行就 `throw`（`question-import.js:45`），50 行表里有 6 处问题就要 6 轮"改一行→重选文件"。→ 解析器改为收集式，逐行标红，给"忽略错误行继续/修好重传"两个按钮。

**（8）导入模板没有媒体列，且只吃 UTF-8 CSV** — 模板 9 列（`question-import.js:1`）不含媒体；只接受 `.csv`（`:2151`）并用 `file.text()` 按 UTF-8 解码（`:1831`）。中文 Windows 的 Excel 另存 CSV 常是 GBK，解析出乱码而报错只说"第 2 行：题型须为…"。
→ 模板加 `mediaUrls`/`answerMediaUrls`/`displayOrder`；接受 `.xlsx` 或检测 GB18030；编码错误明确提示。

**（9）答题/题库没有"玩家会看到什么"的预览** — 编辑对话框只有媒体本身可预览（`:2496`、`:2554`），题干折行、6 个选项在 2×2 网格溢出只能在控场页（`:1539-1545`）发现；改一个字要"保存→切控场→看→切回来"4 次跳转。
→ 对话框右侧常驻小尺寸的玩家端/大屏实时预览（复用真实组件）。

**（10）正确答案靠字母文本框输入，校验只在服务端** — 输入框提示"（逗号分隔）"（`:2411-2420`），但只切英文逗号（`:2027-2030`）；写成"A、C"不会被拆开。保存失败时，服务端返回的英文原因（`Correct answer is not in options`）又被 `api.js:106` 统一替换成"请求参数不正确，请检查填写内容"，具体是哪个字段错了无从得知。
→ 选项做成增删行、行首固定字母，答案用勾选按钮点选；客户端先校验。

**（11）没有未保存守卫** — 题目/题组对话框关闭即 `setDialog(null)`（`:2334`、`:2604`），无 dirty 判定；上传中关闭被静默忽略（点了没反应）。→ 加"有未保存修改，确定放弃？"；上传中按钮改为禁用并显示"正在上传，完成后可关闭"。

**（12）行内不显示答案、不显示引用与作答数** — 题库行只有题干/题型/分值/选项数/启用（`:2172-2210`）；`QuestionAdminResponse` 里也没有引用数或作答数（`ApiModels.java:291-293`）。核对答案必须逐条开框；删除前无从判断后果（有作答时服务端才拒绝，`ActivityService.java:602-603`）。
→ 行内常显正确答案；加"引用题组数""作答数"；有作答的题直接禁用删除并说明原因。

**（13）顺序不可排、保存无反馈** — 新题永远追加到 `displayOrder` 末尾（`ActivityService.java:549`），前端无排序入口；保存成功只是关窗 + `load()`（`:2059-2068`），没有 toast。→ 行内拖拽 + "上移/置顶"；保存成功给"已保存《…》第 N 题 · 查看"。

**（14）一套"状态"五种叫法** — 题目叫"已启用/已停用"（`:2188`），编辑器里同一个布尔叫"允许在控场中发布"（`:2589`），题组叫"当前下发/未下发"（`:2237`）、"保存后立即下发"（`:2671`）、"下发状态"（`:2159`）。而"能上屏 = 题目启用 **且** 在已下发题组里"这条双闸门规则（`ActivityService.java:1155-1169`）界面上从未出现。
→ 统一词表（题目=上架/下架，题组=使用中/未使用）；顶部状态条写「当前使用中的题组：XX（8 题中 6 题上架）」。

**（15）题库的搜索词会越界过滤题组面板，且看不见、清不掉** — 题库 `onSearch` 结果存进 `bankFilters`（`:2171`、`:1781`），题组列表用同一个 query 过滤（`:2108`），但题组面板自己既没有搜索框也不显示关键词（`:2212-2272`）。搜"太阳"→ 题组面板同时只剩含"太阳"的题组，空状态还写"没有匹配的题组"。→ 各自独立筛选，或在界面上显式展示"当前筛选：太阳 ✕"。

### 5.7 参与者

- **要人做的事**：找到某个人，改资料、调分、看他的奖品和抽奖机会。
- **障碍**：
  1. 列表无分页、无排序、无"按会场/状态/积分段"筛选，890 人时一次渲染 890 行；搜索是纯前端 `contains`（`App.jsx:2829`）。
  2. **调分和改资料是同一个 submit**：`积分调整（可正可负）` 输入框和姓名/组织/会场在同一个表单里，共用一个「保存参与者信息」按钮（`:2988-3048`）。想加 10 分的人必须同时提交一遍可能已过期的姓名/组织，容易把别人的改动覆盖回去。
  3. 改分没有"为什么"字段（没有备注/审计理由），事后查不到是谁为什么调的。
- **建议**：
  1. 详情弹层拆两段：「资料」一个保存按钮；「积分」一个独立的小表单（数值 + 理由下拉/备注）+ 独立按钮，提交后立刻回显"新积分 = xx"。
  2. 列表加上分页（50/页）+ 按会场筛选 + 按积分排序。
  3. 列表行右侧加"当前得分变动"最小化展示（最近一次调整）。

### 5.8 奖品与核销

**（1）"现场扫码核销"没有扫码，也不能检索（F21）** — 卡片标题写"现场扫码核销"、按钮写"打开核销器"（`App.jsx:3359-3380`），点开只是 `setRedemptionOpen(true)` + `load()`，渲染一张全部奖项的表格（`:3421-3516`）。没有摄像头、没有输入框、`api.redeem` 只接受 `awardId`（`api.js:351`），服务端也没有按兑换码查询的端点。
200 条记录 × 70px 行高、无内部滚动（`styles.css:45`，`redemption-workspace{overflow:hidden}`）→ 找"李四 · 保温杯"要滚约 14000px。
→ 加"输入/扫领取凭证"（回车 → `/awards/lookup?code=`），默认只列待核销，支持姓名/手机号/凭证搜索。

**（2）核销无确认，成功反馈在页头（F3 同类）** — 行内"核销"直接提交（`:3477-3484`），不展示领取人与奖品；成功提示走全局 notice 渲染在页头（`:3206-3211`、`:3269`），离所点行很远；"反核销"是纯文字按钮（`:3495-3503`），同样无确认。点错相邻行是兑换台最常见的事故。
→ 行内"核销"→ 确认卡片（姓名/奖品/凭证后四位）；成功态固定在该行"已核销，可撤回"。

**（3）手机/平板上"领取凭证"整列被隐藏** — `@media (max-width:810px){ .award-table > article > code { display:none } }`（`styles.css:46`），凭证列只在桌面可见（`:3471-3473`）。而兑换台最常用的设备就是手机/平板，"扫码核销"的承诺在这里彻底落空。
→ 窄屏把凭证码放进行内主信息；让码成为查找主键。

**（4）奖池配置 12 个字段，"触发场景"是工程枚举** — 表单（`:3529-3693`）：编码/名称/触发场景/交付方式/说明/兑换链接/总库存/最低积分/抽奖权重/起始-结束排名/启用。编码需手填且创建后不可改（`:3533`、`:3538`）；场景创建后也不可改（`:3554`）；选错只能删池重建，而删池在已发奖时被拒（`ActivityService.java:953`）。
→ 把"触发场景"换成"谁发奖？"三张卡片；编码由名称自动生成并折叠；场景允许变更。

**（5）配置时看不到"有多少人符合条件"** — 奖池卡只显示剩余/已发放/最低积分（`:3288-3298`），但参与者与奖项其实已经加载（`:3098-3107`），前端完全算得出。库存 1 件 vs 符合 300 人、"最低积分 50 但全场最高 40"这类错要等现场摇奖才暴露（`ActivityService.java:1882`）。
→ 卡片与弹窗顶部实时显示"符合条件 X 人 / 已中奖 Y / 库存 Z"，X=0 红色阻断。

**（6）"抽奖权重"只在一条几乎走不到的路上生效** — 该字段只在 LOTTERY 显示（`:3634-3647`），但主持人摇奖是等概率的（`ActivityService.java:1883` 不读 `drawWeight`），只有"自助抽奖且 URL 不带 `?pool=`"时才按权重在多池间随机（`:1238-1253`），而入口二维码永远带 pool（`:3252-3253`）。运营调了完全没反应。
→ 删除该字段，或改名"多奖池出现的相对概率"并只在自助抽奖入口配置。

**（7）同时开答题与抽奖的会场，排名奖池在 UI 里不可达** — `workspace(lottery ? "LOTTERY" : "QUIZ")`（`:511-512`）让"奖品与核销"页按会场是否开抽奖绑定到抽奖子活动；而 LOTTERY 子活动禁止创建 RANKING 池（`ActivityService.java:920`），UI 也隐藏该选项（`:3562`）。于是这类会场的"排名奖池"和"按排行发奖"按钮永远不出现，运营会以为数据丢了。
→ 该页固定绑定会场，页内 Tab 分"排名奖品 / 摇奖奖品 / 人工发放"。

**（8）自助抽奖的机会只能逐人手动授予** — 唯一入口是弹窗里的单发表单（`:3802-3855`），提交后弹窗无条件关闭（`:3245`）；服务端没有别的授予路径（`ActivityService.java:1008-1018`）。200 人活动 = 200 次"打开弹窗→选人→填次数→提交"；漏掉的人在现场扫码只看到"暂无抽奖机会"，无法自救。
→ 奖池卡加"对全部符合条件者授予 1 次"；提供"登记成功自动赠 1 次"开关；授予后不关弹窗。

**（9）自助抽奖的幂等键不持久化（F27）** — 每次点击现生成 `createIdempotencyKey()`（`:6710`），不写存储（对比主持人端会落 sessionStorage，`:750-751`）。现场网络抖动 → 用户重试 → 服务端两次都成功（`ActivityService.java:1044-1050`），各扣一次机会、各生成一份奖品。
→ 点击瞬间把 key 写 sessionStorage；加载时发现未确认 key 先重放（服务端会返回同一奖项）。

**（10）抽奖前不知道在抽什么奖** — 参与者端只显示"本入口指定奖池 / 剩余 N 次"（`:6746-6750`），从不显示奖池名或奖品名；`preferredPoolId` 从活动选择器进来就丢（`:5865-5866` 来自 URL，`:5990-5994` 不带上），服务端会在所有 LOTTERY 池间按权重随机（`ActivityService.java:1238-1253`）。入口写着"一等奖"却抽到纪念奖，无法解释。
→ 进入即显示"本次可抽：〈奖池名〉（剩余 N 件）/ 你的机会：N 次"，并对 PAUSED／库存 0 在按钮前中文阻断。

**（11）人工发奖可以对同一人重复发放同一奖池** — 发奖弹窗只有"参与者 + 奖池 + 备注"（`:3697-3759`），服务端 `issueAward` 不做"此人此池已中奖"检查（`ActivityService.java:972-980`）。重复发 = 库存多扣 + 该人此后被主持人摇奖永久排除（`:1881`），现场无法解释。
→ 发奖前用已加载的 awards 校验，弹"王五已领过 X"，需显式勾选才能重复发。

**（12）后端给出的原因被前端统一抹平（F36）** — 前端原样展示 `cause.message`，但 `api.js:103-107` 会把所有**非中文**的 `message` 替换成状态码兜底文案。于是"Prize stock cannot be below claimed stock"（`ActivityService.java:943`）在界面上变成"请求参数不正确，请检查填写内容"；中文错误（如摇奖的"没有符合…的参与者"，`:1882`）则正常显示。同一套业务里，一半错误有意义、一半错误只剩状态码。
→ 后端统一返回 `{code, field, zhMessage}`，前端把 `code` 映射成"哪个字段、怎么改"的就地中文提示。

### 5.9 抽奖控场

**（1）停止摇奖即落库发奖，且屏幕上跳动的名字不是中奖人（F22）** — 点"停止并公布中奖人"直接 `api.hostDraw`（`:752`）；滚动名来自本地 `eligible` 数组（`:741-746`），与服务器选人无关；`setDisplayName(winner)` 在响应之后才执行，而 `confirming` 期间（`:754`）大字号 `h2` 仍显示最后滚过的那个名字（`:762`）。
现场效果："停在张三，一秒后变成李四"，主持人与观众都无法解释。停止即发奖、即占库存（`ActivityService.java:1890`），没有确认、没有撤销（撤销要去另一页作废，`:3218-3226`，且作废是终态）。
→ 停止时先用"抽选中…"遮罩盖住名字，落库后一次性揭示；落库前加一次确认（"将向 张三 发放 保温杯？"）。

**（2）大屏只收到"全部获奖名单"，还会覆盖正在进行的答题画面** — 滚动动画只在本机（`:744`），没有任何接口把"摇奖中"推到屏幕；成功后服务端把 stage 置 `WINNERS` 并向该子活动与母会场的所有设备发布整份名单（`ActivityService.java:1893`、`:880-884`）。
若此刻在答题，大屏题目会被名单顶掉，且没有"恢复上一屏"的按钮。→ 新增 DRAWING 展屏态（滚动名字）→ 中奖特写 2~3 秒 → 回名单；不隐式改 stage，提供"回到答题控场"。

**（3）摇奖结果不可回看，"恢复"按钮写着"刷新状态"** — 成功后清空 attempt（`:752`），本页没有"本次结果"区块；超时失败时 attempt 留在 sessionStorage（`:751`），刷新后弹红字（`:726`），唯一出口是 `InlineError onRetry={attempt.current ? stop : load}`，而该按钮文案固定为"刷新状态"（`StaffUi.jsx:12`）——点下去实际会**再发一次抽奖请求**。

### 5.10 海龟汤控场

见 §2.2。再补三条本页独有的问题：

1. **预览面板不可信**（F9）：预览与大屏都按本机 `Date.now()` 推页码（`soupPlayback.js:26`），而 `serverNow()`（`api.js:95`，已带时钟偏移校正）就摆在旁边没用。设备时钟差 20 秒 + 15 秒/页 = 预览和大屏不在一页。**改法**：三端统一用 `serverNow()`。
2. **线索轮播不受暂停控制**（F10）：文案自己承认了（`TurtleSoup.jsx:238`"线索…不受这些按钮控制"）。现场"停一下我解释"是最高频动作，暂停却只停了一半。**改法**：暂停时同时冻结线索轮播（把 `startedAt` 也纳入服务端 playback）。
3. **参与者页在未开始时是空白**（F15）：`if (!data.surface) return null`（`TurtleSoup.jsx:144`）。**改法**：返回"海龟汤即将开始，请留在大屏前"的等待卡（其它抽奖/答题页都有等待态，唯独这里没有）。
4. **短屏静默丢内容**：`@media (max-height:650px)` 会把汤面与线索面板直接 `display:none`（`turtle-soup.css:153-159`），只剩汤底。观众会看到"没有故事只有答案"的画面。**改法**：短屏改为缩小字号 / 单列堆叠（已有 `@container` 规则可复用），不要隐藏内容。
5. **长标题被截断**：大屏标题 `-webkit-line-clamp: 2`（`turtle-soup.css:68`），超出直接省略号，且无滚动。汤名一般较短，但 `title` 上限 160 字（服务端 `Content.title`）。**改法**：超过 2 行时缩小字号至适应，而不是截断。

### 5.12 大屏管理

**（1）「打开受控大屏」会把一次性配对令牌消耗在操作员自己的电脑上** — 配对提示条的第一个动作是 `<a href={pairingUrl} target="_blank">打开受控大屏</a>`（`App.jsx:4198-4206`）；该页一加载就交换令牌并**轮换**（`App.jsx:6831-6841`；`ScreenService.java:159-171`，第 170 行 `rotatePairingToken`），旧链接立即作废。
操作员"顺手点一下看看效果"= 用掉唯一名额；真正的 LED 墙再打开只会得到"大屏配对令牌无效"，而管理端仍显示"在线"。
→ 该链接降级为"仅复制/仅二维码"，点击前确认"本机将占用唯一配对名额"；条内明确写"此链接只能在一台设备上打开一次"。

**（2）78px 二维码 + 链接不可选中：无键盘的播放盒/迷你主机无法配对** — 二维码 SVG 仅 78px（`styles.css:51`），没有放大/全屏；URL 只存在于剪贴板和 `<a href>`（`:4147-4154`、`:4198-4206`），没有只读输入框；`navigator.clipboard` 在非 HTTPS 局域网会抛错（`:4150-4152`），提示"请扫描二维码"而页面上没有可手抄的链接。
→ 加只读 input（聚焦即全选）+ "全屏二维码"按钮（供屏体主机自扫或投到 LED 上）。

**（3）屏幕会话只存 sessionStorage，关标签即永久掉线，而屏上写的是"等待配对"** — 会话丢失后落到 `pairing-required`（`:6811-6825`），服务端令牌已轮换（`ScreenService.java:170`），旧 URL 不可复用；屏体只显示"等待工作人员配对此屏幕…"（`:6916-6935`），没有一句"本屏已掉线、需重新配对"。令牌过期时把后端错误（同样被降级成通用中文）打到屏上（`:6856-6859`）。
→ 屏体端区分「会话丢失」与「等待配对」，给出可执行的恢复步骤；管理端设备行显示"从未配对/已配对/会话丢失"。

**（4）同一把配对码扫第二次必失败，管理端毫无信号** — 首次成功即轮换（`ScreenService.java:169-170`），第二次 401（`:164-166`）；管理端提示条不可关闭、不标记"已使用"（`App.jsx:4186-4217`），设备行仍显示"在线"。
→ 设备行显示"配对状态 + 最近配对时间"（`lastSeenAt` 已有但没渲染）；提示条在首次心跳后自动变「已配对 · 12:03 已使用」并置灰。

**（5）注册完立刻显示"在线"，而这个"在线"是创建时写死的** — 构造器直接 `status="ONLINE"; lastSeenAt=now`（`ScreenDevice.java:75-78`），`getStatus()` 只在 90 秒无心跳后降级（`:140-142`）。从未被打开过的屏也显示绿色"在线"，操作员因此跳过"到屏体机确认页面已开"；真掉线时只有"离线"两字，分不清刚断还是从没连过。
→ 初始状态改 `PENDING`；行内加"最近心跳 12:03"。

**（6）注册表单要手填宽高，10 秒后就被心跳覆盖** — 宽高必填（`:4438-4469`），而屏体每 10 秒上报真实窗口尺寸（`:6864-6871` → `ScreenService.java:348-356`），设备行又把它当"规格"展示（`:4242-4245`）。操作员查了 LED 规格填 3840×1080，10 秒后变成 1920×900，无从解释。
→ 改为"预期分辨率（可选）"，展示"屏体上报 1920×1080 · 最近心跳"，不一致标黄。

**（7）「重新生成配对链接」藏在页尾、无确认、无回执，且不能踢掉配错的屏** — 它是设备栏最后一个文字按钮（`:4338-4344`），点完新链接渲染在页面顶部（`:4186-4217`），不滚动到可视区 → "什么都没发生"→ 再点一次 → 来回作废。已配对会话不受令牌轮换影响，页面没有"断开此屏"，唯一办法是删设备（连带丢失名称/模板/设置，`:4123-4137`）。
→ 移到设备行内、改「重新配对…」+ 二次确认 + `scrollIntoView` + toast；另加「断开此屏」。

**（8）下发没有目标、没有回执，失败提示 10 秒后自动消失** — 每行模板一个"下发"（`:4379-4386`），目标固定是另一栏选中的 `selectedDeviceId`（`:4052-4055`），按钮上不写设备名；成功后只 `await load()`（`:4056`），设备行不显示"当前模板"，没有 toast；而 `load()` 成功即 `setError("")`（`:3919`），10 秒轮询（`:7331`）会把失败提示静默清掉。
→ 按钮写「下发到〈主舞台 LED 屏〉」；设备行显示「当前：〈模板名〉」（`currentTemplateId` 已在数据里）；成功 toast + 高亮该行；错误改常驻 banner。

**（9）编辑模板 = 立刻改动所有正在用它的屏，无预览、无影响范围、无回滚** — `saveTemplate` 保存即广播（`ScreenService.java:88-97`、`:497-501`），屏体收到立刻重拉。为一块屏改标题，所有用同一模板的屏同时跳变；改错只能再改一遍。
→ 拆"草稿 → 预览 → 发布"：弹窗内嵌 16:9 实时预览，保存时确认"将立即更新 3 台在线大屏：A、B、C"，并提供"另存为新模板 / 撤回上一版"。

**（10）没有"清屏 / 待机"，也没有"回到上一屏"** — 本页没有 LOBBY 动作，`setScreenDisplay` 在 `api.js:366` 存在但从未被调用；而答题推送会 `updateDisplay(null, …)`（`ScreenService.java:240`）清掉 `currentTemplateId` 并重置滚动位置（`ScreenDevice.java:91-97`）。段落之间想清屏只能删模板或结束活动；推完题想回到背景板要回本页重新下发，而界面上看不出"模板指派已被清空"。
→ 加「回到待机屏」「恢复上一块模板」；设备行显示「当前：无 / 〈模板名〉」。

**（11）下发只能单台，没有多选/全选** — 点设备行只做单选（`:4235`），`apply` 固定 `deviceIds:[selectedDeviceId]`（`:4052-4055`），而服务端本来就支持多台（`ScreenService.java:207-227`）。6 块屏换同一套内容 = 6 次"点行 → 跨栏 → 下发"。
→ 设备行加复选框 + "全选在线设备"，按钮变「下发到 N 台」。

**（12）滚动滑杆是 0–100000 的盲滑杆，且下发即归零** — `min=0 max=100000`（`:4313-4327`），不知道内容高度，没有"回顶/到底"；每次 `onChange` 250ms 防抖 PUT，拖动时大屏一次次硬跳。自动滚动速度固定 12.5px/s、到底硬跳回顶部（`:7417-7423`），800px 公告要滚 64 秒。
→ 心跳上报 `contentHeight`，滑杆按内容高度渲染；服务端加 `scrollSpeed` 与"到底停留"；仅 `onPointerUp` 提交。

**（13）音量/滚动/字号三根滑杆在多数模式下空转** — `volume` 只传给答题媒体（`:6981`、`:7159-7170`），模板/海龟汤/积分榜都不接；海龟汤还明确忽略像素滚动（`:6937-6941`）；而三根滑杆始终渲染（`:4289-4327`）。模板模式下把音量拖到 0 毫无反应，操作员会以为界面坏了。
→ 按 `displayMode` 条件渲染（TEMPLATE 只留字号+自动滚动；TURTLE_SOUP 只留字号并提示去海龟汤控场调进度）。

**（14）「信息登记二维码」与「活动二维码」编码成同一个地址** — 保存时两个组件都只写 `{label}`（`:4002-4013`），渲染用 `config.url || joinUrl`（`:7034-7043`），而 `joinUrl` 恒为 `/join/{activityId}`（`:7018`）。两块码内容相同，只有说明文字不同；现场引导话术与实际行为不一致，登记率异常也查不出来。
→ `REGISTRATION_QR` 编码 `?intent=register`，或在编辑器里明文显示"此码将编码 https://…"。

**（15）模板编辑器只能表达"1 段文字 + 1 图 + 1 文件"，编辑既有模板会静默丢组件** — `templateToForm` 只取最后一个 TEXT/IMAGE/FILE（`:3959-3983`），`saveTemplate` 按固定 id 重拼最多 5 个组件（`:3992-4025`），而服务端允许 30 个（`ScreenModels.java:25`）。多文字/多图模板点一次"编辑→更新"，多余组件被静默删除。
→ 编辑器改组件列表（上移/下移/删除，保留原 id 以继续支持 `overrides`）；保存前弹"本次将删除 N 个组件"。

**（16）主标题必填 → 无法创建纯图模板** — 标题 `required`（`:4508-4519`），保存总先塞一个 TEXT（`:4000`），而运行时有整屏图片模式 `template-screen--image-only`（`:7014`、`:7023`）——成了死代码。"一张海报铺满大屏"这种最常见需求做不到。
→ 标题改可选；只有一个 IMAGE 时自动进入 image-only；编辑器加"整屏图片"预设。

**（17）图片/背景/文件只能贴外链、无预览** — 三个 `type="url"` 输入框（`:4534-4561`、`:4588-4601`），弹窗内无缩略图；运行时 `<img>` 无 `onError`（`:7046-7054`）。错链只能在大屏上以破图的形式被发现，而观众已经看到了。
→ URL 框右侧加预览缩略图（`onError` 显示红框"无法加载"）；非 PDF 文件明确标注"将显示为一张卡片，观众无法点击"。

**（18）保存/下发/删除没有 busy 态** — 模板提交按钮无 `disabled`、无 loading（`:4602-4605`），`deleteTemplate`（`:4155-4167`）与 `apply`（`:4045-4060`）同样没有；对比"注册大屏"是有 `deviceBusy` 的（`:4470-4473`）。连点两次"保存模板"→ 两个同名模板；连点"下发"→ 滚动位置反复归零。
→ 统一 busy；服务端对"同名+同 components"做幂等。

**（19）预置模板不可编辑也不可删除，且描述与行为不符** — 预置隐藏"编辑"（`:4387-4396`）、"删除" `disabled` 且无 `title`（`:4397-4404`）；而"番剧答题直播"的描述写"展示题目、倒计时和全场答题进度"（`ScreenService.java:370-372`），下发它其实只是一段静态文字（`:215-219`）。新操作员会以为权限不足；下发后观众只看到一句标语。
→ 预置行改「系统预置 · 可复制」+ "复制为自定义模板"；该预置改名"答题背景板"并注明"题目由答题控场推送"。

**（20）首屏 12 个控件里 5 个永久禁用，唯一可点的"下发"必然报错；手机端丢失"管理"入口** — 新会场（0 设备）首屏：注册大屏、新建模板、5×下发、5×删除（全 disabled 无理由）；无设备时"下发"仍可点，点后只在页顶报"请先选择一个受控大屏设备"（`:4046-4048`）。`@media(max-width:810px){ .device-admin-row .row-action{display:none} }`（`styles.css:41`）把设备行唯一的"管理"（改名/删除）入口隐藏且无替代；≤510px 两个"+"图标按钮无法区分（`styles.css:42`）。
→ 0 设备时整块换成单一 CTA「还没有大屏 · 先注册一台」；≤810px 把"管理"改成"⋯"菜单而不是隐藏。

参与者锁屏后点亮，只能靠倒计时猜"能不能答题了""答案公布了吗"。
→ 恢复那一块，做成 44px 固定状态条：左侧活动/会场，右侧"答题中 00:23 / 答案已公布 / 活动已结束"，随阶段换底色。

**（2）重复登记会进入死循环，而唯一的自救入口是 10px 小字** — 登记时先 `register` 再 `participantToken`（`App.jsx:6230-6238`）；同联系方式登录 → 服务端 409 英文消息（`ActivityService.java:383-385`）→ `api.js:106` 把所有非中文消息统一替换成状态码兜底文案，409 变成"操作与当前状态冲突，请刷新后重试"。可这个冲突是**永久性**的，刷新多少次都一样。
真正能救人的"查询已登记的参与信息"是表单最底部一个 10px 文字按钮（`App.jsx:6335-6337`，`.text-button` 见 `styles.css:45`），错误文案从不提它。
→ 把该 409 单独映射成业务错误，并在登记卡上方渲染带按钮的提示"这个手机号已登记过 → 用手机号找回"，点一下即切到找回模式并预填联系方式。

**（3）找回身份要求"会场 + 联系方式"精确匹配，选错会场就是永久失败** — 服务端查找键是 venue+contact（`AuthService.java:130`）；界面只在"仅一个启用会场"时把会场预选（`App.jsx:6255`），多会场一律"请选择所在会场"，失败文案"身份验证失败，请检查登记信息"不说是会场错；会场为空时提交按钮直接禁用（`:6331`）。多会场活动里记不清在哪个厅的人，会在验证码上反复失败直到放弃。
→ 找回只按 contact（活动作用域内）查，命中后回显"你在 A 厅登记"。

**（4）联系方式是唯一身份键，却没有格式校验、没有二次确认、注册后自己改不了** — `<input required>` 没有 type/inputMode/格式校验（`:6286-6296`），字号 13px（`theme-soyo.css:436-448`）；参与者端没有任何编辑入口（"我的信息"是只读 `<dl>`，`:6182-6186`）。拇指在 13px 输入框里敲错一位，身份就永久错了，且自己无法纠正。
→ 加 `type="tel" inputMode="numeric"` + 宽松校验；提交后回显"我们记下的是 138****1234，对吗？"；开放联系方式自助修改。

**（5）验证码 120 秒过期 + 一次校验即作废 + 失败就换码** — `expiresAt = +120s`（`HumanChallenge.java:36`），每次 verify 即 consume（`HumanVerificationService.java:85`），失败只提示"人机验证失败，请刷新重试"（不区分过期），并自动换码清空输入（`App.jsx:6245`）。排队两分钟再点提交 = 必失败，而用户会以为是自己看错了字符。
→ 提交时若无有效挑战先静默换码并提示"验证码已更新"；失败文案区分"已过期"。

**（6）哪些字段必填根本看不出，而且标反了** — 会场/姓名/联系方式/验证码只有原生 `required`，界面无"必填"字样；唯一明确标注"（可选）"的是组织（`:6298`）；反而自定义字段有 9px 橙色"必填"小标（`:6344-6349`）。
→ 三个内置必填字段统一加"必填"，表头写"共 4 项，约 20 秒"。

**（7）登记成功后没有确认页** — `onRegistered` 只把登记卡整体移除（`:6029-6035`），唯一确认是积分卡里 12px 的"已完成现场身份确认"（`:6006-6012`）；未开题时只剩"等待工作人员开题"。用户只能去问工作人员"我登记上了吗"。
→ 插入成功屏"✅ 已登记 · 张伟 / A 厅 / 请把手机屏幕朝上"，3 秒后进入答题页。

**（8）手机首屏被宣传语、0 分积分卡和活动选择器占满** — 渲染顺序：活动下拉（`:5990-5994`）→ 头图（`:5995-6001`）→ 积分卡（`:6002-6015`）→ 登记卡（`:6022-6036`）；移动端 `.participant-sidecopy` 被 `order:-1` 提前。360×640 上到第一个输入框约 500px，键盘弹出后只剩一个字段可见，而她此时积分还是 0。
→ 未登记状态隐藏 sidecopy 与积分卡，活动下拉降级到页脚。

**（9）答题时间到，"选好了没点提交"的人直接失去提交入口** — `canAnswer = QUESTION_OPEN && remaining > 0 && !result`（`:6513`），归零后提交按钮整块卸载（`:6631-6640`），只留一句"本题答题时间已结束"（`:6641`）；服务端同样在 `remaining <= 0` 拒绝（`ActivityService.java:629`），没有宽限。
在会场 Wi-Fi 下，00:01 按下、请求到达时已过点 → 答案丢弃，而她不知道是被时间卡掉的。
→ 到点自动提交已选答案；倒计时最后 10 秒变红加大；服务端对"按下时刻在窗口内"给 3 秒宽限。

**（10）倒计时只有 12px** — 位于卡片首行右侧（`:6572-6578`），字号 12px（`styles.css:192-197`），无进度条、末段不变色。参与者无法预判何时收手。
→ 提到 24px 单独成行；最后 10 秒变红加粗。

**（11）提交后不可修改，且"答案已提交"文案是死代码** — `canAnswer` 含 `!result`，提交后选项禁用、按钮卸载；按钮里 `result ? "答案已提交"` 分支（`:6637`）永远走不到。多选题想补一项，手滑提交就永久定稿。
→ 截止前提供"修改答案"；或在提交前二次确认"提交后不可修改"。

**（12）网络失败后重试用新幂等键，把"已成功"变成"冲突错误"（F34）** — `submit` 里每次现取 `createIdempotencyKey()`（`:6539`）。首次已落库但响应丢失时，重试带新键 → 服务端走到"已答过本题"409（`ActivityService.java:630-631`）→ 又被 `api.js:106` 降级成"操作与当前状态冲突，请刷新后重试"。
答案其实已经计分，屏幕上却写着冲突；她照提示再点还是同一句。→ 幂等键按 (participantId, questionId) 生成并缓存复用；把这个 409 当成功处理。

**（13）刷新或切 tab 后只知道"答对了"，不知道"我选了哪项"** — `question.id` 变化即清空本地选择（`:6488-6493`），恢复时只用 `submission` 还原结果（`:6494-6501`），而 `AnswerResult` 不带 `answers`。从"排行"看一眼回来，四个选项全灰无高亮，她会怀疑系统记错了题。
→ 用 `submission.answers` 反填并置灰；反馈里直接写"你的答案：B. xxx"。

**（14）活动暂停/结束了，答题卡毫不知情，且两句话互相矛盾** — 抢答卡检查了 `PAUSED/FINISHED/CANCELLED`（`:6443-6444`），答题卡连 `activityStatus` 都没收到（`:6471-6481` 无此参数）。结束后 meta 显示"活动已结束"（`:6577`），下一行却写"请等待主持人开题，页面会自动更新"（`:6641`）。她还能点选项，按下去才报错。
→ 非 LIVE 时用整块状态屏替换题目卡；删掉矛盾的等待提示。

**（15）参与身份只存在 sessionStorage，关标签就要重来** — 参与者与令牌都写 sessionStorage（`App.jsx:7674-7688`、`api.js:60-70`）。iOS 回收后台标签是常态，接个电话回来就回到登记页，然后撞上（2）的 409 死循环。
→ 改 localStorage（配合已有的 401 自动续期），加载时先尝试取回身份。

**（16）参与者端没有任何连接状态提示** — `.offline-status` / `.online-status` 只出现在大屏端（`:6894-6899`）；手机端断网时页面只是不再更新。→ 复用同一个连接状态胶囊。

**（17）活动还没开始是一张死页面，不会自动放行** — `ParticipantPortal` 只在挂载时 `load()` 一次（`:5844-5848`），未开放时落到"活动暂未开放 + 选择其他活动"（`:5854`），既不轮询也不订阅。提早扫码的几十台手机，会在主持人说"可以了"之后仍然停在旧页面。
→ 该分支加轮询/订阅自动进入；文案改"活动即将开始，本页会自动进入"。

**（18）抢到第 6 位也写着"抢答成功"** — 文案"抢答成功 · 第 N 位"（`:6461`）对所有名次一视同仁，没有"由你回答"的高亮，也没有震动；窗口关闭后按钮直接消失（`:6460`），只剩一句"等待主持人开题，或本题抢答已结束"。
→ 第 1 位"🎤 由你回答！请起立"+ 震动；2–N 位"已排第 N 位"；未抢到明确写"本次抢答已结束"。

**（19）服务端的具体错误原因在全站被统一抹平** — `api.js:103-107`：非中文的 `message` 一律替换成状态码兜底文案。于是"这个手机号已登记过""题目不属于当前题组""答案不在选项里""库存不能低于已发放"这些**可自救的信息**，在界面上全部退化成"操作与当前状态冲突，请刷新后重试"或"请求参数不正确，请检查填写内容"。
这是全站最"省事但最贵"的一个设计：用户永远不知道真正的原因，工作人员也拿不到可上报的线索。
→ 保留后端中文 `message`；为高频场景（重复登记、已答过、未在题组、库存不足）定义 `code` 并在前端映射成带操作按钮的中文提示。

**（20）奖品在手机上不可点击、不可复制、没有核销码** — 每条奖励右侧有 `ChevronRight`（`:6743`）但整行没有 `onClick`；兑换码是 13px 等宽 `<code>`（`:6738`），不可复制、不可放大、没有二维码；实物奖不渲染核销码，只写"待领取 · 请前往现场领奖处"（`:6733-6741`），而工作人员核销台恰恰靠核销码找人（`:3472`）。
→ 整行可展开详情；核销码配复制 + 二维码；实物奖补领取地点。

**（21）排行页没有空状态，也找不到"我的名次"** — `MobileRanking` 直接 `items.map`（`:6649-6670`），无空列表兜底，无"你第 12 名 / 共 78 人"摘要；高亮只有 `is-self` 底色。刚开局看到空白卡会以为没加载；80 人时最想知道的数字得自己数。
→ 顶部固定一条"你目前第 12 名 / 共 78 人 / 68 分"，列表自动滚到自己。

### 5.15 大屏端

**（1）顶部常驻一条运营管理条，待机屏还在播内部话术** — 大屏始终渲染 `public-screen-toolbar`：logo + "设备已受控"/"连接中断" + 设备名（`:6889-6904`），画布高度写成 `calc(100dvh - 76px)`（`theme-soyo.css:1576`）为它永久让位；出现错误时还把原始报错以"…· 正在自动重试"打在画布上方（`:6905`）。
更糟的是 LOBBY：硬编码"此屏幕已完成安全配对，等待工作人员下发内容。"（`:6944-6951`），完全忽略工作人员下发的 headline/message（服务端 `ActivityService.java:876-879` 已经写好了"现场内容即将开始"）。
开场前、两题之间、结束后，全场看到的都是"屏幕已配对""设备已受控"，甚至"登录已过期，请重新登录"。
→ LOBBY 改成真正的观众待机屏（下一环节倒计时 + 加入二维码 + 当前前三）；设备状态与错误只在断开时以角标短暂出现。

**（2）不显示题目进度** — 参与者卡片有"第 01 / 10 题"（`:6570`），大屏只有题型、提交人数、倒计时（`:7094-7106`），服务端 payload 里也没有题号（`ActivityService.java:833-855`）。观众不知道还剩几题、何时准备离场或抽奖。
→ payload 加 `index/total`，大屏补"第 3 / 10 题"。

**（3）公布答案后会把全部作答明细铺满整屏（F35）** — `screenResponses` 返回该题**全部**提交、无上限（`ActivityService.java:888-902`），大屏逐条渲染成 13/11/10px 的卡片（`:7140-7150`、`theme-soyo.css:85-87`），容器 `overflow-y:auto`。上百人时题面和选项被挤出画面，而大屏没人会去滚动。
→ 默认只显示前 5–8 条 + "共 128 人作答"，字号≥18px；或翻页轮播。

**（4）正确答案没有独占大字条** — 选择题的答案只体现为选项底色 `.is-correct` + 勾选图标（`:7114-7129`），远看差异极小；反倒是文本题有独立的"正确答案"大字块（`:7130-7139`）。
→ 公布答案时插入独占整行的大答案条（"正确答案 B · 三体"，48px 级），选项只作辅助。

**（5）获奖名单看起来像报表** — `ScreenWinners` 复用积分榜列表样式（`:7258-7286`），奖品名放在 `<small>` 里（10px 级，`theme-soyo.css:38`）；名次只有"01/02"编号，一等奖与参与奖同字号；数据源是全部非作废奖项按时间倒序（`ActivityService.java:861-875`），不分轮次/奖池。
1600px 画布上 10px 字约占 1/160 宽，远低于场地可读的 1/40~1/50 量级——中后排看得见名字，看不见她中了什么。
→ 分两态：主态只放"🏆 一等奖 · 张伟 · Switch 主机"（奖品名 60px 级 + 动效），"查看全部名单"再切列表。

**（6）积分榜显示会场原始代码，前三名没有层级** — `venueDisplayName(item.venue)` 调用时没传 venues（`:7248`），于是多会场时观众看到 `hall-a`、`vip1` 这类内部代码；列表无条数上限，超出画布被 `.public-canvas{overflow:hidden}` 直接裁掉；第 1 名与第 30 名除了数字完全同款。
→ 传入 venues 回显中文会场名；前三名做领奖台式样式；固定取前 10 名。

**（7）带音轨的视频/音频默认 `autoPlay` 但没 `muted`，浏览器会拦下** — `ScreenMedia` 统一 `autoPlay loop controls`，从未设 `muted`（`:7202-7226`）。Chrome/Safari 的自动播放策略在"有声音且无交互"时直接拒绝，大屏停在一帧黑屏，需要工作人员上台点播放——而这道题的题干可能就在视频里。
→ 默认 `muted playsInline` + 角落"🔊 播放声音"按钮。

**（8）短屏会静默隐藏汤面与线索** — `@media (max-height:650px)` 直接 `display:none`（`turtle-soup.css:153-159`），观众看到"没有故事只剩答案"。→ 改缩小字号/单列堆叠，不要隐藏。

**（9）大屏一旦丢了会话，就要在观众面前重新配对** — 屏幕会话存 sessionStorage（`api.js:72-82`），丢失后直接渲染"等待工作人员配对此屏幕 / 请在管理端注册屏幕并使用一次性配对链接打开本页面"（`:6879-6885`、`:6916-6935`）；设备被删除也走同一分支（`:6807-6810`）。现场电脑重启/误开新标签，投到大屏的就是这段后台说明。
→ 会话改 localStorage + 静默续期；确需重配时观众只看"大屏正在恢复连接，请稍候"。
